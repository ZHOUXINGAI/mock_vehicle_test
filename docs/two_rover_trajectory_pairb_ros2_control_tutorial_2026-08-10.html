2. 一条轨迹是怎样让小车动起来的

2.1 轨迹不是“一串定时动作”

最初可以写“前进 5 s、右转 3 s”，但地面摩擦、电池电压、轮子差异一变，车就走不到同一个位置。现在的轨迹是按米表示的一串二维点：每个点包含 x_m、y_m 和参考 yaw_rad，相邻点之间还有弧长进度 s。控制器关心“车现在离路径哪里最近、应该向前看多远”，而不是“计时器走了几秒”。

轨迹结构在 src/orin2_trajectory_tracker.py:27；直线、U 形和 S 形生成器分别在 src/orin2_trajectory_tracker.py:996、src/orin2_trajectory_tracker.py:1017、src/orin2_trajectory_tracker.py:1081。

2.2 每个控制周期的六步

  1. 读状态：从 MAVROS 获取位置、速度、姿态、模式和 GPS 健康。
  2. 找路径投影：在当前位置附近寻找最近路径线段，得到进度 s 和横向误差。代码：src/orin2_trajectory_tracker.py:269。
  3. 选前视点：沿路径向前看一段距离。速度高时看远一点，速度低时看近一点。
  4. 合成转向：参考曲率告诉车“这条路本来要弯多少”；横向/航向反馈告诉车“现在还要额外修多少”。核心步骤：src/orin2_trajectory_tracker.py:585。
  5. 限幅：限制最大车体转向角、转向变化率、曲率修正和速度，避免突然 sharp turn。
  6. 发布：转换成 BODY_NED linear.x/linear.y，20 Hz 发给 MAVROS/PX4。

2.3 为什么要有“前馈 + 反馈”

开车过弯的直观例子：看到前方道路本来就是左弯，提前向左打方向，这是“曲率前馈”；如果车已经偏到道路右边，再多向左修一点，这是“横向反馈”。只用前馈会无法抵消轮胎和地面误差，只用反馈则会在进入弯道后才发现偏了，容易滞后和摆动。

本项目把参考曲率、横向误差、航向误差和受限积分组合，再用近似关系把曲率变成 BODY_NED 的转向 bearing。相关函数包括：

  • src/orin2_trajectory_tracker.py:399：读取前方参考曲率；
  • src/orin2_trajectory_tracker.py:478：计算有界反馈曲率；
  • src/orin2_trajectory_tracker.py:526：更新横向误差积分并处理饱和；
  • src/orin2_trajectory_tracker.py:369：限制转向 bearing 的变化率。

2.4 当前控制器到底是什么

当前控制器更准确的名称是：基于 Pure Pursuit 的几何轨迹跟踪器，加上路径曲率前馈、横向误差反馈/积分补偿、车辆适配和速度/转向限幅。它每约 50 ms 读取一次车辆状态并重新计算命令，所以它是闭环自动驾驶；“不是 MPC”不等于“没有反馈”。完整单步入口在 src/orin2_trajectory_tracker.py:585。

Pure Pursuit 把车辆朝向前视点的夹角记为 alpha，前视距离记为 L，用下面的几何关系得到反馈曲率：

feedback_curvature = 2 * sin(alpha) / L

控制器再读取规划路径本身的参考曲率 reference_curvature。可以把两部分理解为：

  • 参考曲率前馈：道路本来要弯多少，车辆提前知道；
  • Pure Pursuit 反馈：车辆当前位置和姿态已经偏了多少；
  • 有限积分：长期向同一侧偏时，逐渐抵消左右轮、摩擦和死区造成的固定偏差；
  • 车辆适配：把几何曲率变成当前 PX4 Differential Rover 能执行的 BODY_NED bearing。

核心合成过程在 src/orin2_trajectory_tracker.py:673 到 src/orin2_trajectory_tracker.py:745。当前实车入口默认使用约 1.10 m 基础前视、0.90～1.80 m 动态范围、1.28 倍反馈适配、0.04 的横向积分增益和 45 deg/s 转向变化率，参数集中在 scripts/run_orin2_outdoor_forward_5m.sh:141。

它也不是普通 PID：主转向量来自车辆、前视点和路径之间的非线性几何关系；代码中的积分项只是消除持续横向偏差。没有直接使用一组 Kp/Ki/Kd 对单个误差做完整 PID。

2.5 它和 MPC 有什么区别

MPC 是 Model Predictive Control，即模型预测控制。它不只问“现在该往哪边修”，而是用车辆模型模拟未来一段时间，比较许多候选控制序列，再选择综合代价最小的一组。只执行第一步，下一周期根据新状态重新求解。

典型 MPC： minimize sum(Qy * lateral_error^2 + Qyaw * heading_error^2 + Ru * control^2 + Rdu * control_change^2) subject to: state[k+1] = vehicle_model(state[k], control[k]) speed / steering / acceleration / safety-distance constraints

2.5.1 一张表看懂差别

比较项当前几何控制器MPC
基本思路投影到路径，寻找前视点，立即计算曲率预测未来 N 步，求解最优控制序列
未来信息通过前视点和参考曲率做局部预判明确计算未来位置、姿态、速度和约束
车辆模型只需少量几何/车辆适配参数需要可信的运动学或动力学模型
约束处理命令算出后再限速、限转向、限变化率把转向、速度、加速度和安全距离直接放入优化
计算量小，20 Hz 运行简单可靠较大，每周期都要运行数值优化器
双车关系Pair B 做高层阶段协调，两车各自闭环可以预测两车未来轨迹，把相对距离纳入代价和约束
主要风险急弯和执行器迟滞需要调前视/增益模型不准、求解超时或权重不当会导致效果变差

形象地说，当前控制器像司机“看着前方一段路持续修方向”；MPC 像司机在脑中同时试演未来几秒的多种走法，然后选择既贴路、又平顺、还不违反限制的一种。

2.5.2 为什么现阶段没有直接换成 MPC

小车阶段的首要目标是验证 Offboard、共享坐标、通用轨迹、Pair B 消息和双车状态机。当前控制器计算便宜、故障容易解释，而且已经在直线、U 形和连续变曲率轨迹上形成实车证据。此时直接引入 MPC，会同时增加车辆建模、求解器实时性、权重选择和约束调试等变量。

MPC 也不会自动修复 GPS 漂移、磁场干扰、坐标系符号错误、PWM 死区、轮胎打滑或 Pair B 过期消息。这些基础状态和执行链必须先可靠，否则 MPC 只是基于错误输入做更复杂的计算。

2.5.3 迁移到飞机时怎样分层

合理演进不是推翻现有系统，而是保持分层：EasyDocking/Carrier 继续生成共享走廊和任务阶段；预测控制层根据两架飞机模型、未来走廊和相对约束生成速度/姿态参考；PX4 仍负责底层姿态、速度和执行器稳定。小车上的几何控制器仍可作为简单基线和故障回退，用来判断新 MPC 是否真的带来收益。

3. 坐标系：为什么图上向左，车身命令可能是负 y

图 3 Field ENU 与 BODY_NED 的用途和方向

Field ENU 是两车共享的地图坐标：+x 向东，+y 向北，yaw 从东向逆时针为正。它适合表达“Carrier 在 Mini 后方几米”“共享走廊朝哪个方向”。

BODY_NED 是每辆车自己的命令坐标：+x 指向车头，+y 指向车体右侧。地图上的目标向量必须减去当前位置，再按当前 yaw 旋转到车体坐标，才能变成“向前多少、向哪边修多少”。

本项目的关键实测：当前 PX4 Differential Rover 的 MAVROS velocity 路径中，差速转向要核验 linear.y；不能直接照搬常见移动机器人用 angular.z 的习惯。发布和 BODY_NED 回读在 src/orin2_outdoor_forward_5m.py:1316 与 src/orin2_outdoor_forward_5m.py:1586。

4.2 PX4 到四个轮子

PX4 rover controller 把前进和转向需求混合成左右两个执行器，输出 MAIN1/MAIN2。Arduino 只看到两侧 PWM，不知道全局轨迹。它负责：

  • 判断 PWM 是否在合法范围、是否超时；
  • 以 1500 μs 为中点处理正反向和死区；
  • 左侧命令同时驱动左前/左后，右侧命令同时驱动右前/右后；
  • 输入无效或命令为零时关闭电机输出。

参数和固定 by-id 检查在 scripts/run_orin2_outdoor_forward_5m.sh:297；Arduino 当前映射见 arduino/d24a_pixhawk_differential_pwm_bridge/d24a_pixhawk_differential_pwm_bridge.ino 和 docs/d24a_current_motor_mapping.md。

5. Offboard 为什么必须用状态机

图 4 单车进入、运动与退出的 fail-closed 状态机

OFFBOARD 不是“调一个 service 就开始跑”。PX4 要先看到持续 setpoint 流，才允许保持 OFFBOARD。正确顺序是：

MANUAL + disarmed + fresh state → 20 Hz 全零预流 2 s → request OFFBOARD，等待 state.mode == OFFBOARD → request Arm once，等待 state.armed == true → 运行轨迹 → 全零 burst → request Disarm，等待 armed == false → request MANUAL，等待 mode == MANUAL

早期脚本在已经观察到 armed+OFFBOARD 后又等待 2 s，消耗了 PX4 的状态/自动解锁窗口。现在只保留进入模式之前的零预流，真实进入后立即开始第一段受限动作。外部 Pair B 启动门在 src/orin2_outdoor_forward_5m.py:2080，核心 live 状态机从 src/orin2_outdoor_forward_5m.py:1284 开始。

最重要的原则：service success 不是车辆状态。代码必须看到 PX4 State 真正变成 OFFBOARD/armed，退出时也必须看到 MANUAL/disarmed。任何中间状态超时都进入零输出恢复，不自动重 Arm。

6. Pair B 到底怎么传命令

6.1 为什么 Orin2 没有 Pair B USB 串口

Orin2 一侧的 Pair B VEHICLE 电台接在 Mini Pixhawk 的 TELEM2。Orin2 程序先把紧凑帧装入 MAVLink TUNNEL，再通过本机 Pixhawk USB 和 MAVROS Router 送到 TELEM2。Orin1 一侧的 GROUND 电台直接通过 CP2102 USB 接 Linux，因此 Orin1 程序直接打开稳定的 /dev/serial/by-id/...。

TUNNEL 适配代码：src/lr24_mavlink_tunnel.py:45；Orin2 ROS2 Router publisher/subscriber：src/lr24_mavlink_tunnel.py:275；实车总控根据角色选择 transport：scripts/run_pairb_staged_chase_live.py:703。

6.2 一条消息有哪几层

LR24 无线字节流 └─ MAVLink 2 TUNNEL（msgid 385，component 242） └─ L2 紧凑帧 ├─ magic = "L2" ├─ version / message_type / payload_length ├─ payload（MiniState、PlanCommand…） └─ CRC16/CCITT

L2 帧头和 CRC 实现在 src/lr24_compact_protocol.py:24 与 src/lr24_compact_protocol.py:176。一条 L2 帧只放进一条 TUNNEL，不拆分、不拼接，因此接收端容易 fail-closed 校验。

6.4 没有同步时钟，TTL 怎么办

两台 Orin 的 monotonic clock 数值不需要相等。发送端只把 timestamp_ms 和 valid_until_ms 的差值当作 TTL；接收端在本地收到消息时重新启动这个 TTL 计时。同时还有本地 watchdog。序号采用 uint32 回绕规则，重复和旧命令被拒绝。安全门在 src/lr24_command_guard.py:51。

7. 双车运动具体如何实现

图 6 计划 8115 的消息与动作时序

7.1 启动前

  1. 两台车分别启动本地 MAVROS 和轨迹 worker，但 worker 被管道 gate 卡在 MANUAL/disarmed，不发布非零 setpoint。
  2. Carrier 从本车 GPS 锁定 FieldOrigin 并广播。
  3. Mini 把自身 GPS/Local Position 转到共享 ENU，持续发送 MiniState。
  4. Carrier 检查本车 ready、Mini health、origin_id、Pair B 会话和现场授权，条件不全就只发 HOLD。

worker 进程包装和 gate：scripts/run_pairb_staged_chase_live.py:391；等待 MAVROS/FieldOrigin：scripts/run_pairb_staged_chase_live.py:644、scripts/run_pairb_staged_chase_live.py:670。

7.2 Mini 先走，Carrier 后走

Carrier 的协调核心是 src/pairb_staged_chase.py:242。它先把阶段从 HOLD 切到 MINI_ACTIVE，向 Mini 发送 TRAJECTORY。Mini 接受后释放本地 worker gate，自行完成 OFFBOARD→Arm→轨迹跟踪。Carrier 同时要求：

  • Mini 已经运动至少 5 s；
  • Mini 相对起点前进至少 2 m；
  • 两车状态与 Pair B 消息仍新鲜。

全部成立后才进入 BOTH_ACTIVE，释放 Carrier 本地 worker。这里的“同时运动”不是同一 CPU 时钟同一微秒起步，而是共享阶段约束下的有界先后顺序。

7.3 Mini 停后 Carrier 为什么还能继续

Mini 完成路线后会 Disarm，因此后续 MiniState 不再带完整 executor-ready health。早期版本可能先收到这个状态，再收到 COMPLETE，于是 Carrier 误判 Mini 故障并跟着停。修复后：

  1. Mini 在第一条停车后 MiniState 之前，立即发送一次 MissionStatus=COMPLETE；
  2. Carrier 对“位置仍有效但 executor-ready 已撤销”的状态提供 500 ms 有界终态等待；
  3. COMPLETE 一旦通过 plan_id/seq/时效验证就锁存，不要求反复重发；
  4. Carrier 继续使用新鲜 MiniState 位置计算终端纵向/横向间距。

终态优先发送：scripts/run_pairb_staged_chase_live.py:595；终端间距计算与停止判定：src/pairb_staged_chase.py:109、src/pairb_staged_chase.py:143。

8. RViz 和日志怎么看

8.1 RViz 只负责“看”，不负责“开”

单车 controller 会发布 planned_path、actual_path、vehicle_pose 和 lookahead_target。双车总控把两车轨迹转换到共享 frame 后发布到 /pairb/carrier/* 与 /pairb/mini/*。当前 RViz 配置按现场要求只显示两条实际轨迹。

可视化代码：src/rover_rviz_trajectory.py、src/pairb_dual_trajectory.py；配置：config/rviz/pairb_dual_trajectory.rviz。即使 RViz 崩溃，控制器和安全状态机仍独立运行。

8.2 单车 mission.log 的阅读顺序

BODY_NED_VERIFIED EXTERNAL_START_GATE_ACCEPTED ZERO_PRESTREAM OFFBOARD_REQUEST_ACCEPTED ARM_ONCE_RESPONSE TRAJECTORY_REFERENCE_LOCKED TRAJECTORY_PROGRESS ... cross= ... curvature= ... body=(x,y) TRAJECTORY_TARGET_REACHED 或 MISSION_ABORT FINAL_RECOVERY_SAFE=True

先看任务是否真的进入 OFFBOARD/armed，再看 reference 是怎样锁定的，然后看 progress/cross/curvature。最后必须看 recovery；只看到“车停了”不等于程序证明了 MANUAL/disarmed。

附录：一句话记忆

  • 轨迹跟踪：先找自己在路上的位置，再看前方一点，结合道路弯度和偏差打方向。
  • Offboard：先用零流证明“我会持续发命令”，再切模式、Arm、运动；结束必须回读安全状态。
  • Pair B：只传任务、状态和急停，不传高频方向盘。
  • 双车：Carrier 决定阶段，两车各自闭环；无线失效时，本车必须能自己停。
  • 定位：普通 GPS 能看大轨迹形状，RTK 才适合收紧末端相对距离。
